## 1. Зачем это нужно

Современный пользователь ждёт, что приложение работает одинаково хорошо и «в метро без связи», и «на даче с плохим интернетом». Заметки, расходы, читалки — всё это должно сохранять данные локально и при этом не терять изменения и не показывать дубли при возврате в сеть.

Наивный подход «сохранил на сервер — забыл» не работает: при потере сети данные пропадают или зависают без обратной связи. Нужен другой сценарий:

- **Локальное хранилище** — источник истины на устройстве, приложение работает офлайн (SwiftData).
- **Очередь изменений** — каждое действие записывается в локальную очередь, чтобы потом «доехать» до сервера.
- **Повторная синхронизация** — при восстановлении соединения очередь отправляется, а с сервера тянутся чужие изменения.
- **Разрешение конфликтов** — если одну запись изменили на двух устройствах, нужно договориться, чья версия победит.

Это классическая **offline-first** архитектура. Обучать нейросети и подключать готовые SDK тут не нужно: вся инженерия — в правильном проектировании модели синхронизации, очереди изменений и правил разрешения конфликтов. И именно эта логика должна быть вынесена в отдельный тестируемый модуль.

## 2. Что должно получиться

1. Пользователь создаёт/редактирует/удаляет заметку — всё работает мгновенно и офлайн.
2. Изменение попадает в локальную очередь, помечается как «ожидает отправки».
3. При появлении сети очередь автоматически отправляется на сервер, с сервера приходят чужие изменения.
4. Если одну запись меняли на разных устройствах, приложение показывает результат разрешения конфликта (например, «победила последняя версия») и не теряет данные.
5. Для уровня П/Э: повторная попытка синхронизации по таймеру при нестабильной сети, отправка изменений в правильном порядке, индикатор статуса синхронизации в интерфейсе, симуляция двух устройств для проверки конфликтов.

Плюс отчёт в PR: описание выбранной стратегии разрешения конфликтов и почему.

## 5. Контракт модуля логики

Тесты проверяют поведение этих типов. Имена можно адаптировать, структуру выбирайте сами. Модуль **не должен** зависеть от SwiftData и от сети — только чистые типы Swift и протоколы.

```swift
// Базовая модель записи (заметка)
struct Note {
    var id: UUID
    var title: String
    var body: String
    var updatedAt: Date        // используется для разрешения конфликтов
}

// Операция в очереди изменений
enum ChangeOperation { case create, update, delete }

struct Change {
    let id: UUID               // id самого изменения (для идемпотентности)
    let noteId: UUID           // какая запись меняется
    let timestamp: Date        // когда сделано на устройстве
    let operation: ChangeOperation
    let payload: Note?         // для create/update; delete может нести nil
}

// Очередь изменений: локальная, сохраняет порядок
protocol ChangeStore {
    func enqueue(_ change: Change) throws
    func pending() throws -> [Change]      // в порядке добавления
    func markSent(_ changeIds: [UUID]) throws
    func clearAll() throws
}

// Транспорт: сетевой интерфейс, отделён от логики
protocol SyncTransport {
    func push(_ changes: [Change]) async throws -> PushResult
    func fetchSince(_ since: Date?) async throws -> [Note]
}

// Результат синхронизации
struct SyncResult {
    let pushed: Int
    let pulled: Int
    let resolvedConflicts: [ResolvedConflict]
}

struct ResolvedConflict {
    let noteId: UUID
    let winner: Note           // какая версия победила
    let loser: Note?           // какая отброшена (или сохранена как дубль)
    let strategy: ConflictStrategy
}

// Стратегии разрешения конфликтов
enum ConflictStrategy { case lastWriteWins, localWins, serverWins }

// Ядро: координатор синхронизации
struct SyncEngine {
    mutating func enqueue(_ change: Change) throws
    mutating func sync(transport: SyncTransport) async throws -> SyncResult
    mutating func resolve(local: Note, remote: Note, strategy: ConflictStrategy) -> Note
}
```

### Правила синхронизации

- **Очередь FIFO.** Изменения отправляются в порядке добавления; изменения к одной записи не переставляются.
- **Идемпотентность.** Повторная отправка одного и того же `Change` (по `Change.id`) не создаёт дубль на сервере.
- **Порядок «операция delete».** `delete` для записи отправляется последним для этой записи, чтобы не «воскресить» удалённое.
- **Отправка и получение.** Сначала пушится локальная очередь, затем тянутся чужие изменения с `updatedAt > lastSyncedAt`.
- **Конфликт** — серверная и локальная версии одной записи разошлись (`updatedAt` и содержимое отличаются). Разрешается по выбранной стратегии.

### Правила разрешения конфликтов (по порядку)

1. **`lastWriteWins` (по умолчанию).** Побеждает запись с более поздним `updatedAt`. Если время равное — побеждает серверная.
2. **`localWins`.** Побеждает локальная версия, она же отправляется на сервер.
3. **`serverWins`.** Побеждает серверная версия, локальная отбрасывается.

Все разрешённые конфликты попадают в `resolvedConflicts`, чтобы приложение могло показать их пользователю (уровень П/Э).

## 6. Тестовые сценарии

Каждый сценарий — отдельный автотест. Модуль тестируется на in-memory реализациях `ChangeStore` и `SyncTransport` — без устройства и без сети.

### Этап 1. Очередь изменений

| № | Действие | Ожидаемый результат |
|---|---|---|
| Q1 | Создать заметку офлайн | `Change(create)` добавлен в очередь, `pending().count == 1` |
| Q2 | Создать, затем отредактировать | Два `Change` в очереди, порядок сохранён (create → update) |
| Q3 | Создать, отредактировать, удалить | Три `Change` в очереди, `delete` идёт последним |
| Q4 | `markSent` для части изменений | Отправленные уходят из `pending()`, неотправленные остаются |
| Q5 | Очередь после «перезапуска» (новая in-memory реализация, изменения переданные заранее) | Все неотправленные изменения на месте |

### Этап 2. Синхронизация

| № | Действие | Ожидаемый результат |
|---|---|---|
| S1 | Очередь с 2 изменениями, транспорт «в сети» | `sync` пушит оба, `pushed == 2`, очередь пуста |
| S2 | Повторный `sync` после успешной отправки | Ничего не пушится повторно, `pushed == 0` |
| S3 | Транспорт бросает `NetworkError` | `sync` возвращает ошибку, очередь **не теряется**, `pending()` сохраняет все изменения |
| S4 | Очередь пуста, на сервере есть чужие изменения | `sync` тянет их, `pulled == N` |
| S5 | Частичная отправка (первое упало, второе ушло) | Отправленное отмечено, неупавшее остаётся, повторный `sync` досылает остаток |
| S6 | Повторная отправка одного `Change.id` на «сервер» | Сервер не создаёт дубль (идемпотентность) |

### Этап 3. Конфликты

| № | Локальная запись | Серверная запись | Стратегия | Ожидаемый результат |
|---|---|---|---|---|
| C1 | `updatedAt` новее | `updatedAt` старее | `lastWriteWins` | Побеждает локальная |
| C2 | `updatedAt` старее | `updatedAt` новее | `lastWriteWins` | Побеждает серверная |
| C3 | разные версии | разные версии | `localWins` | Побеждает локальная |
| C4 | разные версии | разные версии | `serverWins` | Побеждает серверная |
| C5 | запись изменена и локально, и на сервере, время равно | — | `lastWriteWins` | Побеждает серверная |
| C6 | конфликт разрешён | — | любая | Запись попала в `resolvedConflicts` с указанием стратегии |
| C7 | локально удалена, на сервере изменена | — | `lastWriteWins` | `delete` не отменяется: побеждает удаление (запись не «воскресает») |

## 7. Этапы выполнения

### Этап 1. Хранилище и очередь изменений (≈2,5 ч) — обязательный

1. Создайте проект и модуль `SyncCore`, настройте запуск его тестов одной командой (`swift test`).
2. Реализуйте модель `Note`, операцию `Change`, очередь `ChangeStore` и пройдите сценарии Q1–Q5.
3. В приложении: экран списка заметок с локальным хранилищем (SwiftData), добавление и редактирование заметок офлайн.

### Этап 2. Синхронизация (≈2 ч) — обязательный

1. Реализуйте `SyncTransport` (REST/JSON через URLSession) и тестовую in-memory реализацию.
2. Реализуйте `SyncEngine.sync` и пройдите сценарии S1–S6.
3. Подключите транспорт к локальной заглушке сервера; добавьте кнопку/автозапуск синхронизации и индикатор статуса.

### Этап 3. Конфликты и авто-повтор (≈2,5 ч) — обязательный

1. Реализуйте `resolve` и стратегии, пройдите сценарии C1–C7.
2. При восстановлении соединения (`NWPathMonitor`) синхронизация запускается автоматически.
3. Покажите пользователю, что конфликт был разрешён (список `resolvedConflicts`), без потери данных.

После этапа 3 у вас работающий прототип модели синхронизации: приложение работает офлайн, не теряет изменения, догоняет сервер при восстановлении сети.

### Этап 4. Надёжность и реальные сценарии (≈2 ч) — уровень П

1. Повторные попытки синхронизации по таймеру при нестабильной сети (экспоненциальная задержка).
2. Симуляция двух устройств: две in-memory реализации `SyncTransport` с общим «сервером», проверка, что конфликты разрешаются корректно при работе с одного хранилища.
3. Таблица тестов: 5+ сценариев с колонками «локальная версия», «серверная версия», «стратегия», «кто победил».

### Этап 5*. Расширенная модель (≈2 ч) — уровень Э

1. «Локальная» корзина вместо мгновенного удаления: `delete` становится `softDelete`, конфликт «удалено здесь / изменено там» не теряет данные.
2. Хранение очереди изменений и метаданных синхронизации (`lastSyncedAt`, `deviceId`) в той же локальной БД.
3. Версионирование записей (`revision`), которое строже, чем только `updatedAt`.

## 10. Частые проблемы

- **Изменения пропадают при ошибке сети** — значит, очередь очищается раньше, чем сервер подтвердил получение. `markSent` должен вызываться только после успешного `push`.
- **Дубли на сервере** — повторная отправка одного `Change` без идемпотентности. Храните `Change.id` и проверяйте его на сервере.
- **Удалённая запись «воскресает»** — конфликт «удалено/изменено» обрабатывается неверно. `delete` должен отправляться последним и побеждать (или используйте `softDelete`, этап 5).
- **Очередь перестаёт двигаться при нестабильной сети** — нет повторов по таймеру. Добавьте экспоненциальную задержку (этап 4).
- **Конфликты решаются «на глаз»** — без явной стратегии. Сделайте `resolve` чистым и тестируемым (сценарии C1–C7).
- **Тесты логики требуют iOS-рантайма** — значит, в модуль `SyncCore` попала зависимость от SwiftData или UIKit. Модуль должен быть чистым Swift.
- **Не видно, когда идёт синхронизация** — добавьте индикатор статуса (в очереди / синхронизация / конфликт).
